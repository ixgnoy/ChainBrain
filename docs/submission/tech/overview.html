01 Project overview
01 · Project overview

The problem, and who it is for

An AI agent that pays for things today gets either a whole wallet or nothing. With the wallet, one tricked instruction can empty it. Without it, the owner approves every payment by hand, and the agent saves no time.

Who it is for

People and small businesses who want an AI agent to buy small things on its own, such as data, reports or news feeds, without watching every step and without handing over their wallet.

Topic F, Agent Wallet

An AI wallet agent that carries out on-chain payments by itself, with risk control. Every payment in this package is a real transaction on a FISCO BCOS chain that judges can open.

What is new

One card per agentEach agent spends from its own contract with its own balance and rules. A mistake stays inside that card.
Rules checked at the moment of paymentThe token asks the card before any money moves. Our server checks first too, but nothing depends on it.
AI that can only make rules stricterRadar scores sellers, the Sentinel can freeze a card, and memory keeps preferences. None of them can loosen a rule.
An agent that explains a "no"Every refusal comes back with a reason the agent reads. It tries another seller or tells the owner the one change that would help.

02 System architecture
02 · System architecture

Architecture, by who you have to trust

Read it top to bottom. The owner's device holds the only key that can change a rule. Our servers run the AI and can be wrong. The chain at the bottom holds the rules and has the final say on every payment.

Arrows show who calls whom. The green line is the only path that changes a card's rules. The Sentinel's key can freeze a card and nothing else. The agent loop calls the wallet tools; the model never sees a key.

Models, tools, data sources and outside services

AI modelClaude Haiku 5.5 through OpenRouter by default. One setting switches to Anthropic's API or to a scripted agent with no model.
Agent tools7 wallet tools. Only pay moves money, and no tool accepts a payee address (page 4).
Paymentsx402 version 2: the seller answers HTTP 402 with a price, the agent's signed payment comes back in a header, and a facilitator submits it on chain.
Data sourcesSeller content, always wrapped as untrusted; token transfers on the chain, which Radar indexes; an optional risk-label file.
HostingRailway: the chain node, the wallet API, the sellers and the console. A console mirror on Vercel.

A TypeScript service (Hono on Node 24, with viem and the x402 libraries) runs the agent and checks each payment before it reaches the chain. A second process runs the test sellers. Neither holds an owner's key.

Sign-in and accounts

Password-free sign-in with the owner's key, one agent key per card, rate limits, and saved accounts and events.

Payments

The 7 tools, quotes and settlement over x402, the task check, the dry run, owner co-signs, and the 30 refusal reasons.

The agent

The tool loop, the scripted fallback, the model switch, memory, and turning one sentence into card rules.

Safety

Radar's seller screening and alerts, the Sentinel's hold and freeze, and the judges' attack arena on the real chain.

Routines and onboarding

Standing orders checked every 30 seconds, two starter cards for a new account, the faucet.

Chain access

A read-only explorer and RPC proxy, plus the 8 x402 test sellers with 12 items.

03 Agent design
03 · Agent design

How the agent understands, plans and remembers

The model plans, compares sellers and talks to the owner. We assume it can be tricked, so the money rules sit in code and on the chain, not in instructions to the model.

One turn of the agent

The task the owner confirms

Buy: one durian export market report
Price: at most HK$15.00 each, HK$15.00 in total, up to 1 item
Deadline: 2026-10-19 23:59 HKT

The model fills in the fields. Code writes the three lines, so the amounts and the deadline shown are never the model's own words. Each quote, co-sign request and payment is then checked against them: confirmed, not expired, price per item, total, number of items.

Models

Setting LLM_PROVIDERUsed for every AI feature
openrouter defaultClaude Haiku 5.5, or one of four other preset models
anthropicOpus 5.5 for the agent, Sonnet 5.5 for rules, Haiku 5.5 for memory, Radar and the Sentinel
scriptedNo model: a keyword router and fixed parsers

Memory can only tighten

After each turn the model writes a short note per card, up to 30 items. It reads only the owner's words and fixed lines built from wallet events, never seller text. A note that would loosen a limit ("always pay", "raise the cap", "trust this seller") is rejected. Two bad attempts keep the old note.

Rules from one sentence

"HK$5 a week for news, only Exa, ask me above HK$1." The model reads the sentence twice in parallel, and wherever the readings differ, the stricter value wins. The owner sees a draft card with each rule in plain words, and still has to sign it.

The Brain graph

The apps draw the agent's world as a live graph: ChainBrain in the centre, then agents, their cards, and the sellers each card may pay. Every node is a real agent, card or seller, and each line carries a payment count.

Seller text is data, never instructions. Everything a seller returns is wrapped as untrusted content, and fake closing tags are removed. Requests for personal data or for a signature are refused by code. Seller text never reaches memory, the haggler, Radar's summary or the Sentinel's model.

03 Core algorithms · One payment

One payment, step by step

"Get me a durian export report, under HK$15, by tonight." Every message from that sentence to the money landing, and where each check runs.

StepCheckWhat happensRefusal reason
7At the quoteThe card, the task and Radar are checked and reported, so the agent can change plan early. Nothing is refused yet.none
12Task, Radar, SentinelThe price, total, item count and deadline; the seller's risk score; any hold on the cardPRICE_ABOVE_INTENT · COUNTERPARTY_HIGH_RISK · SENTINEL_HOLD
12Dry run, then card rulesThe exact transfer runs as a dry run and its result is recorded but never blocks. Then the card's own check is read from the chainSELLER_NOT_ALLOWED · OVER_CAP · NEEDS_OWNER_APPROVAL
13Live priceThe seller's price at payment time must match the quote: network, token, payee, amountQUOTE_MISMATCH
15The card, on chainThe last check, made by the contract when the money moves (page 8)the transfer reverts

Each refusal carries one of 30 reasons, so the agent can re-plan instead of retrying. A signed payment is valid for 600 seconds and only once. Its one-time number is derived from the confirmed task, so every transfer traces back to it.

03 Core algorithms · The card
03 · Core algorithms

The card's checks

The card is a small smart contract. When a payment arrives, the token asks the card whether the signature is valid (the ERC-1271 standard), and the card answers yes only for a transfer inside the owner's rules.

What happens when a payment reaches the chain

The rules a card holds

RuleWho changes itWhen broken
Sellers it may paythe ownerSELLER_NOT_ALLOWED
Cap per payment, overall or per sellerthe ownerOVER_CAP
Ask-me limitthe ownerthe owner must co-sign that payment
Allowance per day, week or month, Hong Kong timethe ownerOVER_PERIOD, unless the owner co-signs
Expiry datethe ownerPOCKET_EXPIRED
Freezethe owner or the Sentinel freezes; only the owner unfreezesPOCKET_FROZEN
Revoke, for goodthe owner, who can then take the money backPOCKET_REVOKED

What the agent and the owner sign

Both sign the same structured message (EIP-712): from this card, to one seller, one amount, one one-time number, one time window. The token is handed both signatures together:

abi.encode(to, value, validAfter, validBefore,
           nonce, agentSig, ownerSig)

ownerSig is empty when no co-sign is needed. The transfer itself follows EIP-3009, a token transfer anyone can submit once the payer has signed it.

The contracts

Pocketthe card, 216 lines
MockEHKDthe test token, 102 lines
PocketFactorycreates cards, 27 lines
ClockFISCO's time in seconds, 11 lines

Solidity 0.8.24 with OpenZeppelin 5.4, built and tested with Foundry. Every rule change and payment emits an event anyone can read.

04 Security design · Permissions
04 · Security design

Who holds which key

Each key has one limited job. The owner's key is the only one that can change a rule or move money out freely, and it never leaves the owner's device.

KeyWhere it livesCanCannot
OwnerThe phone's secure storage, or the browser with an optional passkeyCreate, fund and edit cards; revoke; unfreeze; take the money back; co-sign one paymentBe seen by the server
Agent, one per cardDerived on the server when needed from a master secret and the card's id; never storedSign one exact transfer from its own card to a seller it was quotedChange a rule, pay a seller not on the list, go past the cap, the allowance or the balance, or sign for someone else's card
Sentinel (guardian)The server; fixed when the card factory is set upFreeze a card, giving a reasonMove money, unfreeze, or change any rule
FacilitatorThe serverSubmit a payment the agent already signedSpend from a card without the agent's signature
Token issuerThe serverMint test Mock e-HKD for the faucet and new accountsTouch any card's rules or balance

If a key is stolen

an agent key
Pays only allowed sellers, under the cap and the allowance. Above the ask-me limit it still needs the owner.
the whole server
The same limits apply to every card. The server's own checks are skipped; the card's are not.
the guardian key
Can freeze cards, which stops payments. The owner unfreezes. No money moves.
an owner key
Full control of that owner's cards, which is why it stays in the device's secure storage.

Signing in without a password

Sensitive actions, by tier

Reading needs nothing. Paying inside the rules needs the owner to confirm the task once. Paying above the ask-me limit or the allowance needs the owner's co-sign for that payment. Changing a rule needs the owner's own transaction.

How a card gets its agent

The app asks the server for the next agent address. The owner's key then creates the card with that agent and the chosen rules, and funds it with a plain transfer. A card can only use an agent issued to its own owner.

04 Security design · Protection
04 · Security design

Protection against injection, escalation and leaks

The layers above the card cut down mistakes. The card is the layer that guarantees the limits. The results of 63 attacks, the data map and the known risks are in the separate security self-assessment.

Radar: who is this seller?

Radar indexes every Mock e-HKD transfer and follows a seller's money three hops each way. Labels come from a risk-list file, plus a "flagged" label for any seller that asked for data or a signature.

Re-screens every 30 seconds; a worse score alerts every card that paid or quoted that seller. The thresholds are a first guess, not yet calibrated.

Sentinel: is this agent hijacked?

SignalWhenAction
Refusal burst3 or more suspicious refusals in 60 sfreeze
Ghost transfermoney left with no payment eventfreeze
Follow-througha refusal within 120 s of a data requesthold
Probing2 suspicious refusals in 60 swatch
Repeated attacks2 chat attacks in 5 minuteswatch
Fast burn80% of the budget in the first 20% of the card's lifewatch

The guardian can only freeze

A freeze is a transaction from the Sentinel's guardian key, which is set once per card. It can't move money, unfreeze or change a rule. Without that key, a freeze becomes a hold.

The AI can only make it stricter

A second model reads a fixed summary and may raise a watch to a hold or a freeze. It can never lower a decision, and a freeze needs at least 70% confidence.

A dry run that never blocks

Before paying, the wallet runs the exact transfer as a dry run and records "pays" or "refused, because". After settling it shows predicted against actual.

Prompt injection: seller text is data (page 6) and the card holds anyway. Privilege escalation: only the owner's key changes a rule (page 9). Privacy: no name, email or ID is collected, and requests for personal data are refused. All 30 refusal reasons are listed in the self-assessment.

What the RPC gateway fixes

Fee history. Wallets ask for fee data that FISCO doesn't have, so the gateway answers with zeros.
Event logs. Large log queries are split into 5-block windows, up to 5,000 blocks.
Batches. More than 8 calls at once are split, and transaction indexes are repaired.
Funding. FISCO needs a sender to hold some native balance, so a protected route gives it.

How to check our results

  • Every hash opens in the hosted explorer.
  • The Python verifier reads a card with only the standard library and compares it with what the owner approved.
  • One script re-fetches all 25 hosted receipts.
  • The console's Evidence tab exports expected against actual for each scene.

Known limits

  • Radar's thresholds are a first guess, not calibrated on real data.
  • The content scan reads JSON fields. A request written as prose is left to the model and the card.
  • Open tasks, quotes, Radar's index and the Sentinel's state reset when the server restarts.
  • One FISCO node. The iOS app was tested in the simulator and Expo Go, not as a store build.
