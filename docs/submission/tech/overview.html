Give your AI a card,
not your wallet.

ChainBrain gives each AI agent its own card: a smart contract on FISCO BCOS that holds Mock e-HKD and the owner's spending rules. The agent finds sellers and pays them. The card checks every payment against the owner's rules at the moment the money moves, so a fooled agent still can't pay outside them.

One payment, start to finish

Each agent, its own card

An agent gets a card and a key that can only sign for that card. A mistake or an attack is limited to that card's balance and rules, never the owner's wallet.

The chain has the last word

Seller allowlist, cap, co-sign limit, weekly allowance, expiry, revoke and freeze live in the card. Code in the server and app checks first, but nothing relies on it.

The owner's key stays on the device

The phone keeps it in the iOS Keychain or Android Keystore; the console keeps it in the browser, optionally behind a passkey. The server never sees it.

Keys and sign-in

Who holds which key

Every key can do one narrow job. The owner's key is the only one that changes a rule or moves money out freely, and it never leaves the owner's device.

KeyWhere it livesCanCannot
OwnerPhone: iOS Keychain or Android Keystore. Console: browser, optionally behind a passkeyCreate, fund and edit cards; revoke, unfreeze, take funds back; co-sign one paymentBe read by the server: it never leaves the device
Agent, one per cardDerived on the server when used: keccak256(AGENT_MASTER_KEY ‖ cardId), never storedSign an exact EIP-3009 transfer from its own card to a quoted sellerEdit a rule, pay a seller off the list, pass the cap, the allowance or the balance, or sign for another person's card
Sentinel (guardian)Server, SENTINEL_PK; fixed in the factoryFreeze a card, with a reasonMove money, unfreeze, or change any rule
FacilitatorSellers service, FACILITATOR_PKSubmit a transfer the agent already signedSpend from a card without the agent's signature
IssuerServer, OWNER_PKMint test Mock e-HKD for the faucet and new visitorsTouch any card's rules or balance

If a key is stolen

agent key
Pays only allowed sellers, under the cap and the allowance. Above the ask-me limit it still needs the owner.
the whole server
Same limits, for every card. The checks in the server are skipped; the card's checks are not.
guardian key
Can freeze cards. Freezing stops payments; the owner unfreezes. No money moves.
owner key
Full control of that owner's cards. That's why it stays in the device's secure storage.

Signing in without a password

What the phone will sign

A signing guard decodes every request first and signs only: creating a card, funding the owner's own card, the owner controls on the owner's own card, and a co-sign whose card, seller and amount match the request shown on screen. Anything it can't decode, it refuses.

How a card gets its agent

The app asks POST /v1/cards/agent for the next agent address, then the owner's key signs PocketFactory.create(agent, cap, askAbove, expiresAt, sellers) and a plain transfer to fund it. A card can only use an agent issued to its own owner.

Smart contracts

The card contract

A card is a small ERC-1271 contract. The token asks it "is this signature valid?" at the moment of payment, and the card answers yes only for a transfer inside the owner's rules.

What the agent and owner sign

Both sign the same EIP-712 TransferWithAuthorization: from this card, to one seller, one amount, one nonce, one time window. The signature handed to the token is an envelope:

abi.encode(to, value, validAfter, validBefore,
           nonce, agentSig, ownerSig)

ownerSig is empty (0x) when no co-sign is needed.

Events anyone can read

PocketCreated(pocket, owner, agent), Spent, Frozen(by, reason), Unfrozen, Revoked, RulesChanged, SellerSet, SellerCapSet, and the token's AuthorizationUsed. The Python verifier rebuilds a card's history from them.

Solidity 0.8.24, optimizer 200 runs, OpenZeppelin 5.4, Foundry. Any owner function still works on a frozen or revoked card, so the owner can always take the money back.

Agent and AI brain

Agent and AI brain

The model plans, compares sellers and asks the owner. It is assumed it can be fooled, so every money rule is enforced in code and on chain, never by the prompt alone.

One turn of the agent

The task the owner confirms

Buy: one durian export market report
Price: at most HK$15.00 each, HK$15.00 in total, up to 1 item
Deadline: 2026-10-19 23:59 HKT

The model proposes the fields; code writes the three lines, so amounts and the deadline are never copied from the model. Every quote, co-sign request and payment is then checked against it: confirmed, not expired, price per item, total, number of items.

Models

Flag LLM_PROVIDERUsed for every role

Memory may only narrow

After each turn a reflection writes one memory note per card (up to 30 items). It reads only the owner's words and fixed lines built from wallet events, never seller text. Anything that would loosen a limit ("always pay", "raise the cap", "trust this seller") is rejected. Bad output twice keeps the old memory.

Speak your rules

"HK$5 a week for news, only Exa, ask me above HK$1." Two model readings run in parallel and any difference takes the stricter value. The result is a draft card plus a plain-words proof of each rule. It never creates the card: the owner still signs.

The Brain graph

The apps draw the brain as a live graph: ChainBrain in the centre, memory around it, then agents, their cards, and the sellers each card may pay. Every node is a real agent, card or seller; each edge is "allowed to pay", with the payment count.

Seller text is data. Everything a seller returns is wrapped in <untrusted_content source="…">, forged closing tags are removed, and requests for personal data or for a signature are refused by code (DISCLOSURE_REFUSED, SIGNATURE_TYPE_NOT_ALLOWED). Seller text never reaches memory, the haggler, Radar's summary or the Sentinel's model.

Security and monitoring

Security and monitoring

Layers stacked from the model down to the token. The ones above the card make the agent better behaved; the card makes it safe. Results of 63 attacks, the data map and the known risks are in the separate security self-assessment.

Radar: who is this seller?

Indexes every Mock e-HKD transfer, then traces a seller's money 3 hops each way. Labels come from a sanctions-style file, plus ChainBrain's own "flagged" label for any seller that asked for data or a signature.

Re-screens every 30 s; a worse score alerts every card that paid or quoted that seller. Thresholds are a first guess, not calibrated.

Sentinel: is this agent hijacked?

SignalWhenAction
Refusal burst3+ refused attempts in 60 sfreeze
Ghost transfermoney left with no payment eventfreeze
Follow-througha refusal within 120 s of a data askhold
Probing2 refused attempts in 60 swatch

The guardian key only freezes

A freeze is an on-chain transaction from the Sentinel's guardian key, fixed per card. It can't move money, unfreeze or change a rule. Without the key, a freeze falls back to a hold.

The AI can only raise

A model (TypeSafe's Jev when keyed, else Haiku 5.5) reads a fixed summary and may raise watch to hold or freeze. It can never lower a decision, and low confidence can't freeze.

Pre-flight predicts, never blocks

Before paying, the wallet runs the exact transfer as an eth_call and records "pays" or "refused, because". After settling it shows predicted vs actual, so a wrong guess is visible.

What the RPC gateway fixes

Fee history. Wallets ask for EIP-1559 fees; FISCO has none, so the gateway answers with zeros.
Log windows. eth_getLogs is split into 5-block windows, up to 5,000 blocks.
Batches. More than 8 calls are split; transaction indexes are repaired.
Funding. A token-protected route gives a new sender the native balance FISCO requires.

Built to be checked

  • Every hash opens in the hosted explorer.
  • The Python verifier reads a card with only the standard library and says MATCH or MISMATCH against what the owner approved.
  • verify-evidence.ts re-fetches every recorded hash.
  • The console's Evidence tab exports expected vs actual per scene.

Known limits

  • Radar's thresholds are a first guess, not calibrated on real data.
  • The content scan reads JSON fields; a request written as prose isn't caught by code, only by the model and the card.
  • Open tasks, quotes, Radar's index and the Sentinel's watch lists live in memory and reset on restart; accounts, cards, memory and events are saved.
  • One FISCO node; iOS tested in the simulator and Expo Go, not on a device build.
